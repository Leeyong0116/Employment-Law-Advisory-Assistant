# Plan: M2 indexing

Status: done 2026-10-08 (devlog `docs/devlog/2026-10-08_m2-indexing.md`); approved 2026-10-08 (decisions 1 to 3 as recommended; decision 4
deferred to M4). Written 2026-10-08.

## Goal

Load the 1,852 chunks from `data/processed/chunks.jsonl` into a searchable
index, so that M3 (hybrid retrieval and reranking) has something to query:

- **Dense** search: bge-m3 vectors in PostgreSQL + pgvector, filterable by
  jurisdiction, statute and status inside the SQL query (CLAUDE.md).
- **Sparse** search: BM25, so direct section-number lookups ("section 60E")
  work as well as natural-language questions. bge-m3's own learned sparse
  weights are stored too, as the alternative configuration CLAUDE.md names.

Out of scope for M2: reranker, combining dense and sparse results,
abstention threshold, generation, API. Those are M3 onwards.

## Components

### 1. Database: PostgreSQL 16 + pgvector in Docker

pgvector has no official Windows build; compiling it needs the Visual C++
toolchain. The official `pgvector/pgvector:pg16` Docker image has it ready.
One-off setup by the user: install Docker Desktop (needs admin rights and a
restart; it enables WSL 2). After that, `docker compose up -d` starts the
database from a `docker-compose.yml` committed to the repo, with data kept in
a named volume.

Table `chunks`: one row per chunk.

| Column | Type | Purpose |
|---|---|---|
| `chunk_id` | text, primary key | |
| `doc_id`, `jurisdiction`, `statute`, `section`, `chunk_type`, `status` | text, indexed | SQL filters |
| `content` | text | the embedded text |
| `metadata` | jsonb | all 40 chunk fields, so nothing is lost |
| `embedding` | vector(1024) | bge-m3 dense, HNSW index, cosine distance |
| `sparse` | jsonb | bge-m3 learned sparse weights (alternative config) |
| `index_version` | text | which build produced the row |

### 2. Embeddings: bge-m3

- `FlagEmbedding`'s `BGEM3FlagModel`, fp16 on the GPU; one pass gives both
  the dense vector and the sparse weights. 1,852 short chunks: about one
  minute on this GPU.
- **Only `content` is embedded**, as CP1 and CLAUDE.md fix. (See decision 3
  for BM25.)
- Model downloaded once (about 2.3 GB) into the Hugging Face cache.

### 3. BM25

- `bm25s` (pure Python, fast) over all chunks; 1,852 documents fit in memory
  trivially. Saved to `data/processed/index/bm25/`.
- Filtering by jurisdiction happens by restricting the candidate set before
  scoring, with the same filter values the SQL uses.
- The tokenizer keeps section ids whole ("60E", "2(1)", "121AU"), or a
  query for "section 60E" would match every chunk mentioning "60".

### 4. Build command

`python -m src.indexing.build`:
1. Reads `chunks.jsonl`; `index_version` = short SHA-256 of that file.
2. Embeds in batches; loads the model, then frees GPU memory (CLAUDE.md:
   one model at a time).
3. Upserts every chunk into Postgres; deletes rows from older versions.
4. Builds and saves BM25.
5. Writes `data/processed/index/manifest.json`: index version, model
   names, chunk count, build time. Re-running on unchanged chunks is a no-op.

`index_version` matters later: browser chat history (frontend) stores it per
answer, so a stale citation after re-ingestion can be detected.

### 5. Smoke checks (sanity, not evaluation)

`python -m src.indexing.smoke` runs a handful of fixed queries and checks
the expected chunk is in the top 5. They prove the index works; RAGAS on the
gold set (M3+) measures how well.

| Query | Filter | Expected in top 5 |
|---|---|---|
| "How many days of annual leave am I entitled to?" | Peninsular | EA s.60E |
| "section 60E" (BM25) | none | EA s.60E |
| "maternity leave how many days" | Sabah | Sabah "eligible period" definition or s.83 |
| "maternity leave" | Sarawak | Cap. 76 s.84 or its A1754 amendment |
| "can my employer dismiss me for joining a union" | none | IRA s.5 |
| "essential services" | none | IRA First Schedule |

## Tests (written first)

- Unit, no GPU or database: row mapping from a chunk to table columns;
  tokenizer keeps section ids; manifest and no-op rebuild; embedder and
  database behind small interfaces with fakes.
- Integration, marker `db` (skipped if Postgres is not running): build into
  a test schema, every chunk present once, filters return only matching
  jurisdictions, vector dimension 1024.
- Corpus-level: the smoke checks above.

## Order of work

1. User installs Docker Desktop. (The only manual step.)
2. `docker-compose.yml`, database schema, tests.
3. Install the Python packages and pin them in `requirements.txt`.
4. Embedder, BM25, build command, tests.
5. Full build; smoke checks; record results in the devlog.

## Decisions needing approval

1. **PostgreSQL via Docker Desktop** rather than a native Windows install.
   (Recommended: pgvector has no official Windows build.)
2. **BM25 in Python (`bm25s`)** rather than a BM25 extension inside
   PostgreSQL (ParadeDB). (Recommended: fewer moving parts; dense filtering
   stays in SQL as CLAUDE.md requires; 1,852 chunks need nothing heavier.)
3. **BM25 indexes citation + section title + content; dense embeds content
   only.** Citation text in BM25 is what makes "section 60E" lookups work;
   the dense side keeps the CP1 rule unchanged. (Recommended.)
4. **Generator hardware** (M4): resolved in principle. The user has Sunway
   University HPC access (Open OnDemand; RM 2,000 allocation; 25 GB personal
   and 500 GB group storage). Suitable GPUs: NVIDIA L4 or A10G (24 GB);
   T4 (16 GB) works but is slower; the fractional L4 (3 GB) is too small.
   Likely split: database and retrieval on the local machine; retrieval
   results saved to file (retrieval is deterministic); generation and
   evaluation run as HPC jobs. HPC clusters usually forbid Docker
   (Apptainer instead), which this split avoids. Detail in the M4 plan.
